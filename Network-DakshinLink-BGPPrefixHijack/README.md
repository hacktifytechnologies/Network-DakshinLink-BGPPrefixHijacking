# DakshinLink Route Interception - v3.0.0

This package rebuilds the carrier-style challenge around the complete
intended HTB Carrier learning chain while using current, supportable
open-source components.

## Functional attack chain

1. Real Net-SNMP disclosure of a deployment-generated chassis serial
2. Portal login where the default admin password equals that serial
3. Support documents containing live, deployment-generated AS topology
4. Support ticket identifying the live protected FTP subnet
5. Authenticated base64 diagnostic command injection
6. Real SSH execution as root on the isolated R1 router
7. Three live FRRouting autonomous systems with direct AS2-AS3 peering
8. Selective `/25` origination from R1 toward AS2
9. `no-export` plus an outbound deny toward AS3 to prevent looping
10. Recurring real clear-text FTP client traffic
11. Actual credential interception from packets transiting R1

## Runtime allocation

The setup script dynamically allocates and persists:

- public HTTP and UDP SNMP ports
- six collision-checked Docker networks
- every internal interface and endpoint address
- three unique private ASNs and router IDs
- instance/container/network/hostname suffixes
- chassis serial, FTP username, FTP password and SSH key
- the two more-specific prefixes derived from the live FTP subnet

Values are stored only in operator-owned files under:

```text
/opt/network-challenges/carrier-dakshinlink-route-interception/runtime/
```

Both files are mode `0600`. No Red or Red-vs-Blue command contains a
deployment address, participant address, callback address, ASN, serial or
FTP credential.

## Intentional design constants

The following are not deployment values and remain fixed because they
define the vulnerability or protocol:

- TCP/179 for BGP
- username `admin`
- weak SNMPv1 community `public`
- error codes `45009` and `45010`
- standard Entity-MIB serial OID
- portal endpoint names
- fictional Indian organisation and portal names

## Isolation and telemetry

R1 is a real FRRouting router inside an isolated container. Root command
injection does not grant root on the Ubuntu/Docker host. The host
`frr.service` manages the R1 FRRouting appliance and remains the scored
systemd unit.

Telemetry is generated by the real components and written below `/opt`:

- Apache access/error logs and portal JSONL audit
- Net-SNMP log
- R1 OpenSSH and FRRouting logs
- live R1 packet capture for SSH, BGP and FTP
- R2/R3 FRRouting logs
- vsftpd protocol log and recurring client transfer log

Red-vs-Blue does not use an attack TTP. Blue sees the actual corresponding
Red participant's service requests, injected command, callback session,
routing changes and intercepted packets.

## Deployment

Use a disposable Ubuntu 22.04 challenge VM with internet access for initial
package installation and Docker image builds:

```bash
sudo bash deps.sh
sudo bash setup.sh
```

`setup.sh` is idempotent for this scenario and prints `Setup Successfully`
after live service, BGP, SNMP, portal, direct-path and FTP validation.
